## Goal
Build the scraper adapter for **Save-On-Foods** (https://www.saveonfoods.com): given a search query (and optionally a branch), return the products and prices the site shows. This task needs an agent that can browse the live site and run code (e.g. Claude Code, Gemini CLI, or a browser-enabled agent). A chat-only model can't do it properly; if that's you, say so in NOTES and return only the investigation plan.

## Contract
- `scrapers/adapters/saveon.ts`: `export const adapter: RetailerAdapter` with `retailerId: "saveon"`, `search(query, ctx, branchRef?)`, and optional `findBranches(near, ctx)`. Types in CONTEXT (`scrapers/types.ts`).
- `scrapers/notes/saveon.md`: your investigation notes.
- Use only `ctx.fetchText`, `ctx.fetchJson`, `ctx.newPage`, and `ctx.log` for network access (they enforce delays, caching, and block detection). Use `parsePrice`, `parseSize`, `parseMultiBuy` from `../parse` to fill `RawProduct` fields only if helpful; raw text fields are fine.

## Scraping rules (non-negotiable)
- Check the site's `robots.txt` first and never request disallowed paths. Record what you found.
- One request at a time per store, at least 2.5 seconds apart (BE-01's `fetchText`/`fetchJson` enforce this; always use them or `ctx.newPage()`).
- Ordinary browser behaviour only: normal desktop Chromium or plain fetch with ordinary headers. **No** stealth plugins, rotating proxies, CAPTCHA solvers, fingerprint spoofing, or anything that defeats bot protection.
- If the site shows a CAPTCHA, a bot challenge, a 403/429, or requires login: throw `BlockedError` with the reason and stop. That is a valid, expected outcome; report it.
- Public product prices only. No accounts, carts, or personal data.

## Investigation (write findings in `scrapers/notes/saveon.md`)
1. Fetch `https://www.saveonfoods.com/robots.txt` and note relevant rules.
2. In a real browser (Playwright headed is fine), search the site for "salted butter". Note whether prices require choosing a store first and how a store is chosen (cookie, URL parameter, header, local storage, API parameter).
3. Watch the network requests. If a JSON endpoint returns search results with prices **and** works with a plain `ctx.fetchJson` call with ordinary headers **and** isn't disallowed by robots.txt, use it: it's faster and more stable.
4. Otherwise drive the search page with `ctx.newPage()` and either read the rendered product tiles or capture the JSON response via `page.waitForResponse`.
5. Record: the endpoint or page URL pattern, how branch selection works, fields available (sale flag, was/regular price, multi-buy text, unit price, size), and any blocking you hit.
Confirm everything against the live site; don't rely on remembered endpoints.

## Adapter behaviour
- `search`: return up to 20 `RawProduct`s for the query: `title`, `brand`, `sizeText`, `price` (what you pay now for one), `regularPrice`, `wasPrice` (struck-out price, if shown), `onSale`, `multiBuyText` (e.g. "2 for $5.00"), `unitPriceText`, `url`, `storeRef` (branch id used, if any). `status: "ok"` with products, `"partial"` if some fields are missing, `"blocked"` via thrown `BlockedError` caught by the runner.
- Branch pricing: if the site supports choosing a branch, apply `branchRef` and implement `findBranches(near)` returning nearby branches with the site's own store id as `scrapeStoreId`. If not supported, ignore `branchRef` and say so in the notes.
- Produce priced by weight: put the per-kg or per-lb text in `unitPriceText` and the displayed price in `price`.
- Keep it to one search request (or one page load) per call.
